# Gigl

A Letterboxd-style app for live music. People log shows they've been to (a festival set or a gig found through search), rate them, and rank them. Mobile-first and built for one-handed use.

## Stack

- Next.js 14.2 (App Router), React 18, TypeScript, Tailwind CSS 3.4
- Supabase (Postgres + auth). `supabase-schema.sql` is append-only: new DDL goes at the end and is run by hand in the Supabase SQL editor.
- Ticketmaster Discovery API and independent venues' own websites (show catalogue), setlist.fm (older shows, live), Twilio (SMS show scoring, `/api/sms/*`)
- **Sign-up is by phone** through Supabase Phone auth: `signInWithOtp` then `verifyOtp` in `components/PhoneCodeForm.tsx`, which both `/auth` and the sign-up sheet use. Supabase delivers the codes through its Send SMS hook (Authentication → Hooks), which points at Prelude (prelude.so) and is configured in the dashboard, not in code. Email and password sign-in only remains for older accounts.
- **`/admin` is the owner's control room**, for the admin accounts listed in `lib/adminAuth.ts`: today's QR funnel, whether texted codes are being entered, the latest logs with a Remove button, and the sign-up switch. The switch is the `signup_method` row in `app_settings` (`phone` or `email`). The sign-up screens read it each time they open (`lib/signupMethod.ts`), so flipping it needs no deploy; `email` puts back the pre-phone screens (`components/EmailSignUpSheet.tsx`, `components/EmailAuthPage.tsx`), the fallback for when texts stop getting through.
- Vercel project `gigl-app`: production deploys from `main` and is served at www.gigl.space (the bare gigl.space redirects there). The old address, gigl-review.vercel.app, is printed on Gigl's existing QR codes, so `next.config.js` forwards it to gigl.space and counts a hit on its bare domain as a scan (`app/qr`). The separate Vercel project `gigl` is a broken duplicate on the same repo; its failing checks can be ignored.

## Commands

- `npm run dev`, `npm run build`
- `npx tsc --noEmit` to type-check (there is no test suite or lint script)

## Things that have bitten us

- **Next 14 caches `fetch` indefinitely, including supabase-js requests.** A GET route handler that reads Supabase needs `export const fetchCache = 'default-no-store'` (see `app/api/shows/search/route.ts`), or it keeps serving its first result forever.
- Show search reads the `shows` table, which `/api/cron/sync-shows` refills nightly at 09:00 UTC. That route needs `CRON_SECRET` and `SUPABASE_SERVICE_ROLE_KEY`.
- **Ticketmaster will not page past 1,000 results for one query, and says nothing when it truncates.** This is a hard ceiling per querystring, not a page limit you can raise — a city with more listings than that simply loses the remainder. Measured live: Las Vegas 2,806 upcoming music events, New York 1,937, Chicago 1,208, so one-query-per-city was silently dropping 2,951 events. The sync now reads `totalElements` off the first page and, for any city over `TM_RESULT_CAP`, re-asks in month-sized slices — each slice gets its own 1,000-result budget. Anything new that queries Discovery in bulk needs the same treatment, and the symptom to watch for is a suspiciously round result count.
- **Every city is queried twice, by name and by radius, and both are load-bearing.** A `city`+`stateCode` query matches the venue's city field; a `latlong`+`radius` query matches geography. Measured across all 148 cities: radius found **5,848 events the name query never returns** (venues in surrounding towns nobody named), and the name query found **1,223 radius never returns** — a venue Ticketmaster lists without coordinates cannot match a geographic filter at any radius. Dropping either pass silently loses thousands of shows. The large overlap costs nothing to collect, since ids dedupe it.
- **The nightly sync is four seconds from its own timeout if it runs serially.** `maxDuration` is 300 and a strictly serial walk of 148 cities measured 292s — the run is latency-bound, not rate-bound, because Ticketmaster takes ~850ms to answer. The fetching is therefore concurrent (`CONCURRENCY`) behind a single shared rate gate that hands out request slots 250ms apart, so overlapping the waiting never raises the request rate. If you add cities, windows, or another provider to this route, re-time it rather than assuming it fits.
- **`SYNC_CITIES` is 148 metros chosen by measurement, not instinct**, and their `lat`/`lng` are the median of real venue coordinates rather than civic centroids. Canadian cities carry `countryCode: 'CA'`; a Canadian city queried under the default US country code returns nothing. Adding a city costs one request a night against a 5,000/day quota the sync uses well under a tenth of — so the bar for including a small market is low.
- **Search serves the past week, but the sync fetches what's upcoming.** Gigl logs shows you went to, so `/api/shows/search` only ever returns shows that have already happened — `PAST_WINDOW_DAYS` in `lib/dates.ts` is the window, and browse results run newest first. The sync can't fetch that week, because **Ticketmaster's Discovery API has no past events at all**: an explicit past `startDateTime`/`endDateTime` returns zero results (verified — the same query with no date range returns 800 upcoming). So the catalogue *captures* shows while they're still upcoming and lets them age in place. Two rules hold it together, and breaking either empties search with no way to refill it:
  - `prunePastShows()` deletes a row a full year (`RETAIN_DAYS`) **after** its date, never the morning after — longer than search reaches, because people come back to look up older shows. Those rows are the only record the show existed.
  - Future-dated rows are never deleted. Each one is an advance capture of a show that enters the past week in a few days.
  A missed nightly run is therefore a permanent hole, not a stale day: a show that happens while the job is broken and wasn't captured earlier can never be logged. There is no live-Ticketmaster fallback in the search route any more — the only thing it could return is upcoming shows.
- **Shows from before the catalogue began come from setlist.fm, live, and are never stored.** `/api/shows/past` (see `lib/setlistfm.ts`) settles the exact artist first (setlist.fm's own setlist search matches names so loosely that "the national" returns orchestras before The National), reads that artist's shows from the past five years (`LOOKBACK_YEARS`) two pages at a time, and when that comes to a handful (`FEW_SHOWS`) also tries the query as a venue — "casbah" is a band with three shows and a San Diego room with hundreds. Each load returns a `next` cursor (`a:3` artist pages, `v:3` venue pages) that "Show earlier shows" passes back; reading five years up front would burn the daily quota on one busy touring act. It drops anything the catalogue already has. Its terms shape all of it: **non-commercial use only** (charging for Gigl needs a licence first), a followable "via setlist.fm" credit wherever its data appears, and **no copies beyond short-term caching** — so results are never written to `shows`, and a show only reaches the database inside someone's own log. `logged_shows` carries its own artist/venue/date and never reads `shows` back, which is what makes that work. The key (`SETLISTFM_API_KEY`) allows 2 requests a second and 1,440 a day; every request waits for its own slot 550ms after the last, answers are kept in memory for 6 hours ahead of that, and Next's Data Cache keeps 200s across instances. Firing test searches back to back from a script will still earn 429s. If the "More shows" list goes quiet, look for `[setlistfm] ... HTTP 429` in the logs.
  - **A logged show's setlist comes from setlist.fm too, only on a tap.** The Setlist panel on a show's page and a review page (`components/SetlistPanel.tsx`) asks `/api/setlist` → `findSetlist()` when someone taps "See what they played", never on a page view, since every artist page would otherwise spend quota. It searches by artist name pinned to the show's date (one request; the bare headliner is tried when a title like "X with Y & Z" finds nothing), keeps only acts named like the log's, and picks between two setlists on one date by venue, then city. Nothing is stored; answers, "none" included, are kept 6 hours in memory (1 hour for a show from the last 3 days, while fans are still adding it) and an hour at Vercel's CDN, and the panel credits "via setlist.fm" with a link to that setlist's page.
- **Venue websites are the third source of shows, read nightly by `/api/cron/sync-venues` (10:00 UTC, an hour after Ticketmaster).** `lib/venues/list.ts` holds ten independent rooms in each of the 20 most populous US cities; the sync reads each one's own site for schema.org Event JSON-LD, The Events Calendar's WordPress API, a Squarespace events collection or a linked .ics feed, following one same-site "Calendar"/"Shows" link when the home page has none. Rows get `source = 'venue'` and ids `venue-<venue id>-<date>-<act>`, and any show the catalogue already has from Ticketmaster or a user is dropped, so one show is never split across two ids. The WordPress and Squarespace formats answer for the past too, so those venues arrive with up to a year of history. What it can't read is a calendar a ticketing widget draws in the browser (DICE, See Tickets, Eventbrite embeds): those venues report "No events". It obeys robots.txt, names itself `GiglBot`, and fetches one page at a time per site. **It writes only when `/admin` says Live** (`venue_sync_mode` in `app_settings`, dry when missing); every run, dry or live, saves a per-venue report that `/admin/venues` shows. Its own run, not part of `sync-shows`, because that one has no time to spare.
  - **A promoter can stand in for a room** (`promoter: true` in `lib/venues/list.ts`). Some rooms sell only on DICE and have no site of their own, so neither Ticketmaster nor a venue site has them: Reframe Studios in LA is booked by Framework, whose WordPress site lists every show. A promoter's events are filed under whichever venue each listing names, and are deduped per room. A WordPress site whose home page carries no Events Calendar markup is still tried at `/wp-json/tribe/events/v1/`, which is how Framework's feed is found.
- **Ticketmaster files a real share of concerts under no category at all, and `classificationName=music` never returns them.** The "Undefined" segment held four of nimino's late-2026 dates and Ninajirachi at The Fonda. `/api/cron/sync-unclassified` (09:30 UTC) asks for that segment in every city and keeps an event only at a venue that already has music-category Ticketmaster rows, unless the title (`NOT_A_SHOW`) or the room's name (`NOT_A_ROOM`) reads as comedy, theatre or film. Comedy clubs are the trap: they list the odd music night, so they pass the venue test, and before `NOT_A_ROOM` existed Hollywood Improv and Brea Improv were nearly half of what LA and Denver kept. It is a separate run because `sync-shows` has no time to spare.
- **Bandsintown is not usable as a show source as things stand.** Its Data Applications terms limit the API to artists and people acting for them unless Bandsintown approves the app, allow only session caching, and forbid mixing its events with other sources without telling them apart, so its events can't be written to `shows`. Artist-based tour dates wait on the JamBase key instead (`scripts/jambase-probe.mjs`), or on written approval from Bandsintown.
- **User-submitted shows are never pruned, and that is load-bearing.** `/add-show` writes rows with `source = 'user'` through `/api/shows/submit`. A Ticketmaster row can be re-fetched while it's still upcoming; a hand-typed one cannot be recovered from anywhere, so `prunePastShows()` skips them entirely and `submitted_by` is `on delete set null` rather than a cascade — delete the account, keep the show. Writes still go through the service role: `shows` has **no** client insert policy, deliberately, so the validation and duplicate checks in the route can't be bypassed via PostgREST. The route needs `SUPABASE_SERVICE_ROLE_KEY` and returns a clean 503 without it (so it does not work in local dev unless you add the key).
- **"Near me" search is a bounding box, not PostGIS.** `/api/shows/search` takes optional `lat`/`lng`/`radius`; `lib/geo.ts` turns that into a lat/lng box the query filters on, then trims the corners with a real haversine distance. Coordinates come from `lib/useNearby.ts` in the browser, are rounded to 2 decimal places before going in the URL, and are never stored. Rows with a null `lat`/`lng` never appear in a nearby search, and a nearby search never falls back to live Ticketmaster — that path has no location filter. A typed city (`components/CityPicker.tsx`, `/api/shows/cities`) resolves to coordinates from the catalogue itself, with no geocoder, and goes down this same path, so it has the same null-coordinate gap.
- **Local dev and preview deployments use the production Supabase project.** Anything you do in dev writes real rows. The QR funnel (`site_events`, read through the `analytics` views at the end of `supabase-schema.sql`) only counts requests to the production hosts for this reason — see `isCountedHost` in `lib/visitor.ts`.
- **iOS zooms into any text field under 16px when it's tapped, and doesn't zoom back out.** Every `input` and `textarea` is `text-base` (use `fieldInput` from `components/ui.tsx` where it fits). The viewport, with `maximum-scale=1` as a backstop, is `export const viewport` in `app/layout.tsx`. A hand-written viewport `<meta>` in `<head>` does nothing, because Next's own tag comes after it and wins.
- **Saved shows stay private, and a reminder has no stored state of its own.** `saved_shows` (see `lib/savedShows.ts`) is owner-only under RLS, because where someone will be is more sensitive than where they've been. Each load works out what's due: a saved show that has passed, isn't dismissed and has no `logged_shows` row with `artist_id = show_id`, so logging a show is what ends its reminder. The catalogue is read at the same time, which is how a rescheduled date moves the saved row, and a Ticketmaster row the sync stopped seeing more than three days before its date counts as probably cancelled and isn't prompted. Reminders are in-app only so far. `text_opt_in_at` records consent for texts, but nothing sends them until carrier (A2P 10DLC) registration is done.
- **Reporting, blocking and in-app account deletion are App Store requirements** (Apple guidelines 1.2 and 5.1.1(v)); don't remove them. The ••• menu (`components/ContentMenu.tsx`) on feed cards, comments, artist-page reviews and profiles files `reports` and `blocks`, and `/admin` shows open reports to act on. A block hides each person's logs and comments from the other through the read policies on `logged_shows` and `show_comments` (`private.is_blocked_with`), so it only applies to reads made with the viewer's session: server components that read Supabase without one (`/u/<name>`, `/artist/<id>`) still show everything. `/delete-account` → `lib/accountDeletion.ts` deletes only the files in the user's own storage folder, never paths taken from `media_urls`, which a log's owner can point at anyone's file.
- **Tags of who you went with are saved through the pending-log queue, not straight to `show_tags`.** A new log has no id until `flushPendingLogs()` upserts it, so the log screen queues the tagged ids beside the payload (`taggedUserIds`, never inside it: the payload is written to `logged_shows` as it stands) and the flush writes them with `syncShowTags`. Undefined means "leave this log's tags alone", which is what a save does if an existing log's tags never finished loading. A tag made by writing `@username` in the review lasts only as long as the @ does; see `lib/tags.ts`.
- **Two artist routes, on purpose.** `/artist/<id>` is one show's page of reviews (the id is the show's, from `logged_shows.artist_id`); `/artists?name=…` is every show Gigl has for an artist, and `/venues?name=…&city=…&state=…` the same for a venue (`lib/shows/history.ts`). Both are opened from the Feed's search (`/api/search`, `components/FeedSearch.tsx`), which also lists shows to log or save, so the Log button isn't the only way in. They match names exactly, ignoring case, so a respelled artist is a different page. They ask setlist.fm for older shows straight away only when there are fewer than five past shows to list; anything else waits for a tap, because every artist page visit would otherwise spend up to five of the 1,440 requests a day.
- **Sharing a show has two links.** A review is `/r/<handle>/<show id>` (`components/ReviewLanding.tsx`), keyed on the pair a log is unique on so the link exists before the queued log reaches the server; `?b=1` hides the stars until the viewer has rated too, and "Were you there? Rate it" opens `/log-show?...&returnTo=` back to it. An upcoming show you saved is shared as an invite, `/i/<token>` (`lib/invites.ts`, `show_invites` and `invite_rsvps` at the end of `supabase-schema.sql`): it copies the one show so `saved_shows` stays private, and only `get_show_invite()` reads it by token. Link previews are drawn by `/api/og/invite` and `/api/og/review` (`lib/ogCard.tsx`, `next/og`). **`next/og` can't render on Windows in `next dev`** (a font path bug): check those images on a preview deployment.
- **Ratings are stars out of 5.** Each log has two 1–5 star sub-ratings, performance and venue, and `lib/rating.ts` averages them into the show score (`computeShowScore`, `isRated`). Never display or store ratings on a 10-point scale. **Crowd is gone:** the log screen no longer asks for it and no score counts it, old logs included, so every score means the same thing. `logged_shows.crowd_rating` still holds older logs' values, and the SMS scoring flow (`/api/sms/webhook`) still records one; nothing reads it.

## Design system

`DESIGN.md` is the source of truth for Gigl's visual language, **Warm Riso Zine**: paper and cream surfaces, dark-brown ink, a burnt-sienna accent, 1.5px ink borders with hard offset shadows, and Space Grotesk + Inter. **Read `DESIGN.md` before creating or changing any UI.** `/design` (`app/design/DesignPreview.tsx`) renders every pattern with sample data. It only exists in local dev and preview deployments.

How to apply it:

- **Build UI from the shared pieces, not raw classes:**
  - `components/ui.tsx`: `Card`, `Label`, `Chip`, `Stars`, `ArtistPhoto`, `PersonPhoto`, `Place`, `DateTag`, `Segmented`, `BackHeader`, the `btn*` recipes and more
  - `components/AppHeader.tsx` for the main tabs' header, `components/BottomNav.tsx` for the dock, and `components/Logo.tsx`
  - `DESIGN.md` section 4 maps each pattern to its component.
- When you need raw classes, use the Tailwind tokens:
  - colours: `paper`, `cream`, `cream-alt`, `ink`, `ink-muted`, `ink-faint`, `accent`, `accent-hover`, `terra`, `star`
  - `font-display` / `font-sans`, `border-1.5`, `rounded-card`, `shadow-riso` / `shadow-riso-lg`, `tracking-label`
  - Use opacity modifiers for tints (`bg-accent/10`, `border-ink/15`) rather than new hex values.
  - **Don't pass a conflicting class to a component that already sets it** (for example a text colour to `Label`, or a font size to `Logo`). Tailwind doesn't let the later class win reliably. Use the component's prop instead (`tone`, `size`), or add one.
- Icons come from `lucide-react`.
- **A rating is only ever shown as stars.** Use `Stars` (it wraps `components/StarDisplay.tsx`, which handles partial fills). Don't add numeric scores or tier descriptors (Elite, Epic, Top Tier…). The unlinked legacy `/rank` page still shows Elo numbers.
- **Photos:** pass artist photos to `ArtistPhoto` from `useArtistImages` (client) or `getArtistImages` (server), and profile photos to `PersonPhoto` from `profiles.avatar_url`. Anything without a photo shows the placeholder. "Where the photos come from" in `DESIGN.md` explains the sources.
- Features marked *(mockup)* in `DESIGN.md` exist only in the style guide: filter chips, gig map, streaks, goals, milestone callouts and city rank. Don't build them without asking. Reviews, highlight tags, friend tagging, photos and the following filter are real.
- **Festival theming is not carried forward.** Ignore festival-specific screens and themes (Bonnaroo, Outside Lands) when designing. No screen uses `useTheme()` / `lib/theme.ts` any more; `FestivalThemeProvider` in `app/layout.tsx` and the unused `components/SmsScoringSection.tsx` are the only things left touching them.
